# FastAPI + uv + Docker

A minimal example of packaging a FastAPI application into a
Docker image. Dependencies are managed with **uv** (`pyproject.toml` +
`uv.lock`); a single **Dockerfile** builds the
image.

## What you will learn

- how `uv` replaces `pip` + `requirements.txt`;
- what a Docker **image** and a **container** actually are;
- why the Dockerfile copies `pyproject.toml` *before* the source code
  (layer caching);
- what `ENV PATH="/app/.venv/bin:$PATH"` does, and why the container
  won't start without it;
- that containers are ephemeral: in-memory data dies with the container.

## Project structure

```text
student-api/
├── app/
│   ├── __init__.py      # empty; makes "app" a Python package
│   └── main.py          # the FastAPI application
├── .dockerignore        # files excluded from the build context
├── .python-version      # pins the Python version for uv
├── Dockerfile           # the recipe for the image
├── pyproject.toml       # project metadata + dependencies
├── uv.lock              # exact pinned versions (generated by uv, commit it)
└── README.md
```

## Prerequisites

- [uv](https://docs.astral.sh/uv/): install with
  `curl -LsSf https://astral.sh/uv/install.sh | sh`
- Docker

## Step 0: run locally (no Docker yet)

```bash
uv sync                               # creates .venv, installs deps, writes uv.lock
uv run uvicorn app.main:app --reload
```

Open <http://127.0.0.1:8000/docs>: FastAPI auto-generates interactive
documentation (Swagger UI).

> `uv.lock` must exist and be committed **before** `docker build`: the
> Dockerfile runs `uv sync --frozen`, which installs exactly the locked
> versions and refuses to resolve anything new.

## Step 1: build the image

```bash
docker build -t student-api .
```

Watch the output: steps marked `CACHED` are layers Docker reused from
previous builds.

## Step 2: run the container

```bash
docker run --rm -p 8000:8000 --name student-api student-api
```

| Flag | Meaning |
|---|---|
| `-p 8000:8000` | forward host port 8000 → container port 8000 |
| `--name` | human-readable name for `docker stop` / `docker logs` |
| `--rm` | delete the container automatically once it stops |

## Step 3: call the API

```bash
curl http://localhost:8000/
curl http://localhost:8000/students

curl -X POST http://localhost:8000/students \
     -H "Content-Type: application/json" \
     -d '{"id": 2, "name": "Bob", "course": "DevOps"}'

curl http://localhost:8000/students/2
```

## How it works

### What uv does

`pyproject.toml` declares *what* we depend on (`fastapi>=0.115`). `uv.lock`
records *exactly* which versions were resolved. `uv sync` installs precisely
those versions into `.venv`. The same result on every laptop and in every
Docker build: this is what replaces `requirements.txt` + `pip`.

### What the Dockerfile does

1. starts from a slim Linux image with Python 3.12;
2. copies in the uv binary;
3. installs dependencies from the lockfile, an expensive, therefore
   cached, layer;
4. copies the source code, a cheap layer that changes often;
5. exposes port 8000 and starts uvicorn bound to `0.0.0.0`.

**Why manifests before code?** Docker caches each step. If only
`app/main.py` changed, the dependency-install layer is reused (`CACHED`)
and the rebuild takes seconds.

### Image vs container

An *image* is a frozen, read-only snapshot: OS + Python + dependencies +
your code. A *container* is a running instance of it. One image → many
containers. Everything a container keeps in memory disappears when the
container is removed, then the image itself never changes.

## Deep dive: `ENV PATH="/app/.venv/bin:$PATH"`

Try this: remove the line from the Dockerfile, rebuild and run.

```text
docker: Error response from daemon:
exec: "uvicorn": executable file not found in $PATH
```

The container refuses to start. Here is why step by step.

### 1. How a command is found

When the container starts, Docker executes the `CMD`, i.e.,  it must find an
executable file named `uvicorn`. It is **not** searched for "everywhere on
disk", but only in the directories listed in the `PATH` environment
variable, colon-separated, from left to right:

```text
PATH=/app/.venv/bin:/usr/local/bin:/usr/bin:/bin
       ↑ uv installed uvicorn here        ↑ system tools
```

### 2. Where uv actually installs things

`uv sync` never touches the system Python. It creates an isolated virtual
environment, `/app/.venv`, with its own `bin/` directory containing
`python`, `uvicorn` and friends. The base image's system Python in
`/usr/local/bin` knows nothing about them, so without a `PATH` entry,
`uvicorn` is invisible.

### 3. Why not just "activate" the venv, like we do locally?

Two facts:

- `CMD ["uvicorn", ...]` uses **exec form**: Docker calls the executable
  directly, with no shell involved. There is no `bash` session that could
  run `source .venv/bin/activate`.
- "Activating" a venv does essentially one thing: it prepends the venv's
  `bin/` directory to the current shell's `PATH`. So setting
  `ENV PATH=...` in the Dockerfile *is* the activation, baked into the
  image, no shell required.

A shell-form workaround (`CMD . .venv/bin/activate && uvicorn ...`) would
technically work, but then the shell becomes PID 1 and swallows the
`SIGTERM` sent by `docker stop`, breaking graceful shutdown. Exec form +
`ENV PATH` is the correct pair.

### 4. Prepend, not replace

`"/app/.venv/bin:$PATH"` puts the venv directory *first* and keeps the
original value after it. System tools (`ls`, `sh`, `curl`) keep working,
and in case of a name clash the venv binaries win.

### 5. A pleasant side effect

`ENV` applies to *any* process in the container, not just the `CMD`, so
exploring the image is easy:

```bash
docker run -it student-api bash   # interactive shell inside the image
uvicorn --version                 # works immediately, no activation needed
python                            # resolves to /app/.venv/bin/python
```

Note for the curious: `uvicorn` is a small script whose first line
(the shebang) is `#!/app/.venv/bin/python`, so once found via `PATH` it
automatically runs with the venv's interpreter and its packages. `PATH`
only handles the first step: "find the command".

### Alternatives (and why we don't use them)

| Variant | Why not |
|---|---|
| `CMD ["/app/.venv/bin/uvicorn", ...]` | works, but verbose; in an interactive session you'd type full paths by hand |
| `CMD ["uv", "run", "uvicorn", ...]` | needs uv at runtime and adds an extra layer of indirection |
| `pip install` into the system Python | loses isolation, then why use uv at all |

## Experiments

1. **Layer caching.** Change the greeting in `app/main.py`, rebuild the
   dependency step shows `CACHED`, the build takes seconds.
2. **Ephemeral state.** POST a student, stop the container (Ctrl+C), start
   it again, the student is gone. Containers are throwaway; persistent
   data belongs in a database or a volume.
3. **Many containers, one image.** `docker run --rm -d -p 8001:8000 student-api`
    same image, second container, different host port.
4. **The PATH lesson.** Comment out `ENV PATH=...`, rebuild, run, read
   the error message. Then put the line back.

## Troubleshooting

- `exec: "uvicorn": executable file not found in $PATH`
  → the `ENV PATH` line is missing.
- `port is already allocated`
  → another container (or a locally running uvicorn) uses port 8000;
  pick another host port: `-p 8001:8000`.
- Dependencies changed but the image still has the old ones
  → make sure `pyproject.toml` / `uv.lock` were updated; force a rebuild
  with `docker build --no-cache`.
